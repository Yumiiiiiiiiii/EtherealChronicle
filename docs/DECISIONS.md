## Foundation implementation decisions (Codex, Task 1)
- One YAML document per stable `ec:` ID; a generated content-index includes every shipped YAML. All twelve content-type folders are installed. Existing content is preserved; differences from shipped defaults are logged so admins can compare required fields after upgrades. Schema hooks run before validation; unsupported versions fail closed.
- Player schema 2 migrates unversioned/v1 saves, including tutorial state, into a per-quest progress/completion map. YAML IO runs on a serial background queue. Atomic same-filesystem moves are required; unsupported atomic rename fails visibly instead of silently weakening the guarantee. Primary corruption is quarantined before restoring a verified backup. Future schemas never fall back to an older backup.
- Starter delivery consumes its entitlement durably before adding inventory items (at-most-once delivery). A server crash or disconnect in that narrow window can lose delivery; an administrator can explicitly recover with `/ec starter <player>`. This deliberately favors no duplication across the independent Paper inventory and plugin save files. Inventory writes remain on the server thread. A true cross-store exactly-once grant requires a later durable inventory outbox.
- Admin class changes preserve XP, quests and starter entitlement, while resetting selected skill, class skill ranks and resource. They do not grant another starter kit. Equipped items with unmet conditions contribute no stats.
- Per-second resource/HUD updates use only online player profiles. A private 60-second counter flushes dirty profiles. Quit/disable enqueue detached final snapshots. Normal IO is asynchronous; shutdown deliberately waits for the IO queue to drain before the plugin exits. In-memory cooldowns survive reconnects, expire during cleanup and reset on plugin/server restart.
- F cycles skills; sneak + right click on slot 9 also cycles. Right click with an RPG weapon casts the selected skill, replacing normal bow drawing for RPG bows. Interactable blocks remain usable without sneaking. Slot 9 holds a protected skill item; a former bound item is relocated within the inventory or retained until space is available. Only an unbound former item may drop when reserving the slot.
- Task 1 mobs are explicitly admin-spawned; vanilla spawn reasons never attach RPG rewards. This prevents split/spawner farms until bounded spawn points land in Task 2. Right-click targeting requires line of sight.
- Simulation profiles use deterministic UUIDs in a separate `simulation/` directory and share real GameService/SkillEngine/PlayerStore code. Console commands: `ec debug sim join <name>`, `class <name> ec:mage`, `skill <name> [skill]`, `kill <name> ec:forest_slime`, `quest <name> ec:tutorial`, `dump|save|load <name>`. Quest completion refuses incomplete or already rewarded objectives.
- Paper API 26.3 build 257 declares SnakeYAML 2.2 in its POM; compile/test dependency now matches 2.2 and is not shaded. Better Design is outside Minecraft UI scope per lead clarification.

## Chapter 1 implementation decisions (supersede foundation details above)
- Player schema 5 stores quest objectives/history/repeat eligibility, flags, bounded recent transaction IDs, daily shop counts, accessory selection, pending_rewards and per-table/item drop_pity counters. Schema 4 and earlier saves initialize pity to empty through migration. Class aliases migrate ec:warrior/archer/mage to canonical ec:class_* IDs. Retired tutorial state maps into the Chapter 1 onboarding flow. Existing physical legacy PDC items migrate where their old definition was removed.
- Normal vanilla inventory remains movable. Runtime transactions run on the main thread, stage changes, lock the player and roll back on synchronous failure. Buying debits and persists pending outputs before physical delivery. Selling and token exchange remove inputs and call player.saveData() before payout persistence (explicit lead-approved main-thread IO exception). Debug logging marks that boundary. Potions omit forced Paper saves to avoid per-drink disk IO; they use normal inventory persistence.
- Pending outputs survive ordinary disconnect and disable; claims retain the mailbox when inventory is full. Claim delivery persists removal of the entitlement before physical issue. A tracked in-flight claim is restored on quit/disable. This is not a cross-file atomic transaction under abrupt process/power loss; RELEASE documents recovery and residual windows. No WAL was requested for v1.
- Content installation records normalized hashes and retires unchanged removed shipped files into retired-content. For upgrades, it refreshes an active file only when its bytes match the previous shipped hash, first archiving the old bytes under content-history; modified/untracked files are preserved. A one-time manifest of the original foundation files supports upgrades from pre-manifest installs. Invalid server content reports the file and ID and boots on validated bundled defaults; validate/reload remain available. Administrators reconcile genuinely edited stale files themselves.
- The demo generator builds bounded floating islands/bridges in a newly owned ec_world; ownership/build markers use Paper's actual worldFolder. Unknown pre-existing worlds are refused. Sanctum instances use separated regions in this world, with cached arena construction, participant sets, caps/timeouts and return locations. No user world is deleted or regenerated. First-time arena construction remains bounded synchronous block work.
- Enemy AI and boss attacks are generic data-driven shape/trait handlers, not bespoke scripts for every lore description. Drops use independent rolls with bounded per-profile pity only on explicitly authored entries; no class-biased pool exists. REVIVE is an accessory-only lethal damage guardian passive; its right-click path prints an equip instruction and never consumes it. Twelve initial class skills remain the authored damage skills, with optional area/heal/buff support in the engine.
- Expanded console simulation uses real QuestEngine, DialogueEngine, TradeEngine, PartyService, GameService and virtual mob HP services. Virtual bags/conversation/party state are memory-only and explicitly reset on sim load/restart; only fake profiles persist under simulation/. OPEN_SHOP/ENTER_DUNGEON dialogue effects report their intent without GUI/teleport. This does not verify real Player events or represent a persistent game economy.
